`bongvis/IDENTITY.md` 5절의 흐름을 그대로 따른다. 템플릿은 `templates/*.json` 에 있다.

> **작성 전에 [`bongvis/HOUSE-STYLE.md`](../bongvis/HOUSE-STYLE.md) 를 반드시 읽는다.** 최상단 구성·범위 한정·강조 기호·다이어그램 비율·출처 하이퍼링크·HTML 산출물·게시 전 4단 게이트가 거기에 있다. 도구는 `scripts/` 에 있으니 재발명하지 않는다.

## 0. 설정 확인

`~/.bongvis/user.json` 과 프로젝트의 `bongvis.team.json` 이 있는지 확인한다. 둘 다 없으면 `/setup custom` 으로 안내하고 멈춘다. 있으면 조용히 읽고 진행한다(다시 보여주지 않는다).

## 1. 질문 — 정확히 이 순서, 이 세 개만

`$ARGUMENTS` 로 문서 종류/입력 소스가 이미 주어졌으면 해당 질문은 건너뛴다.

**질문 형식** — 여러 질문을 한 번에 묻지 않는다. 하나씩 번호로 묻고, 각 질문의 보기는 a/b/c 로 매겨 고르게 한다(자유 서술로 묻지 않는다. `AskUserQuestion` 사용 가능하면 그걸로 묻는다).

**Q1. 문서 종류** (2단계)
- 1차: a) 기록(회의록) b) 결정(ADR) c) 요구(PRD·FRD) d) 설계(TDD)
- c) 를 골랐으면 2차로 a) PRD b) FRD 중 확인

**Q2. 입력 소스** — a) 이 대화 b) 파일 경로 c) URL d) 붙여넣기 e) 없음(인터뷰로 채움)

**Q3. 언어** — `user.json` 의 `default_language` 를 기본값으로 제시하고 한 줄로 확인만 받는다.

절대 묻지 않는다: 미리보기 여부(항상 함), 게시 여부(미리보기 후에 사람이 정함), 말투(설정에 있음).

## 2. 재료 수집

Q2에서 정한 소스를 실제로 읽는다(파일 Read, URL은 WebFetch, 대화는 이 세션 컨텍스트). 소스가 "없음"이면 템플릿의 각 섹션 `ask` 문구로 하나씩 인터뷰한다.

## 3. 템플릿 로드 및 필수 항목 확인

`templates/<종류>.json` 을 읽는다. `sections[].required: true` 인 항목마다 재료에서 답을 찾는다. 못 찾은 항목만 모아서 한 번에 되묻는다 — 빈칸을 추측으로 채우지 않는다. `unknown`/미확인 항목은 채우지 못했다고 해서 비워두지 말고 "확인 필요"로 명시해 채운다.

## 4. 용어 적용

`bongvis.team.json` 의 `glossary` 를 재료와 대조한다. `avoid` 목록의 표현이 나오면 `term` 으로 바꾸고, 문서 끝에 "용어 교정" 항목으로 무엇을 바꿨는지 남긴다. 용어집에 없는 새 용어가 재료에 3회 이상 나오면 등재를 제안한다(임의로 정하지 않는다).

## 5. 작성

- front matter: 템플릿의 `front_matter` 필드 채움. id 체계를 이 플러그인이 새로 만들지 않는다 — 프로젝트에 이미 문서/결정 번호 대장(예: `00-plan/decisions.md` 같은 로컬 ledger)이 있으면 그 번호 체계를 그대로 따르고, 없을 때만 잠정 번호를 매기고 확정 아님을 표시한다.
- 본문: 템플릿 `sections` 순서대로, `style` 을 따른다. 대화 말투(`user.json.tone`)는 본문에 절대 반영하지 않는다 — 수치·근거·미확인 항목은 있는 그대로 쓴다. 자료의 출처 성격(실측/외부 리서치/추정)이 섞여 있으면 항목마다 구분해서 표시한다 — 다른 데서 가져온 수치를 이 프로젝트의 실측처럼 쓰지 않는다.
- 다이어그램: 템플릿 `diagram.when` 조건을 충족할 때만 넣는다. 조건 미충족이면 넣지 않는다. 한 문서에 3개를 넘기지 않는다 — 넘으면 문서를 쪼갤지 사용자에게 확인한다.
- 미결 하위 쟁점: 본문 결정과 별개로 아직 못 정한 하위 쟁점(예: 대안 경로 하나만 따로 미확정)이 있으면 본문에 섞어 얼버무리지 않는다. 프로젝트에 결정 로그가 있으면 거기에 별도 항목으로 올리고, 없으면 문서 끝에 "미결 쟁점" 절로 분리해 남긴다.
- 문서 간 링크: 관련 문서가 있으면 `related`/`supersedes` 를 채운다. 같은 주제의 기존 문서가 이미 있으면 작성 전에 알리고 개정(`/revise`)으로 유도한다.

## 6. 로컬 미리보기

작성한 마크다운을 그대로 보여준다(Stage 1 — Confluence 연동 전이므로 마크다운 자체가 최종 미리보기). `bongvis.team.json` 의 `publish.targets` 가 비어 있으면(Stage 1 기본) 여기서 로컬 파일로 저장하고 끝낸다.

## 7. 게시 (`publish.targets` 에 이 문서 종류의 대상이 있을 때만)

1. 이 문서 종류에 맞는 대상을 `publish.targets` 에서 찾는다. 사용자가 특정 폴더/페이지 ID 를 직접 지정했는데 `publish.targets` 의 정본과 다르면 **추측해서 진행하지 않는다** — 다음 중 어디에 게시할지 `AskUserQuestion` 으로 먼저 확인한다: a) `publish.targets` 의 정본 위치 b) 사용자가 지정한 위치(정본에 없음, 새로 등록할지도 함께 확인) c) 게시 보류.
2. 대상이 정해지면 사람이 미리보기를 확인한 뒤에만 "게시할까요"를 한 번 묻는다. 게시 전 질문은 이것뿐이다.
3. `publish.method` 가 `script` 면 `publish.script_path` 의 기존 스크립트를 그대로 호출한다 — 게시 로직을 새로 만들지 않는다. `mcp`/`rest` 면 해당 경로로 게시한다. 스크립트가 정본 밖 게시를 막는 자체 안전장치(예: `--confirm-outside` 류 플래그)를 갖고 있으면, 1번에서 사람이 이미 확인한 경우에만 그 플래그를 사용한다 — 안전장치를 우회하는 새 코드를 짜지 않는다.
4. Confluence 대상이면 storage format(XHTML) 변환 결과를 다시 보여주고, 변환 중 깨지는 요소(표 병합·Mermaid 매크로·이미지)가 있으면 목록으로 먼저 보고한다. 게시 승인 없이 쓰지 않는다.

## 8. 마무리

저장 경로(또는 게시 URL)를 보고하고, `.bongvis/training.json` 에 이 문서 종류의 피드백 대기 상태를 남긴다(`/train` 이 나중에 채움).
