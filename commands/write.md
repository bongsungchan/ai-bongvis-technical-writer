`bongvis/IDENTITY.md` 5절의 흐름을 그대로 따른다. 템플릿은 `templates/*.json` 에 있다.

## 0. 설정 확인

`~/.bongvis/user.json` 과 프로젝트의 `bongvis.team.json` 이 있는지 확인한다. 둘 다 없으면 `/setup custom` 으로 안내하고 멈춘다. 있으면 조용히 읽고 진행한다(다시 보여주지 않는다).

## 1. 질문 — 정확히 이 순서, 이 세 개만

`$ARGUMENTS` 로 문서 종류/입력 소스가 이미 주어졌으면 해당 질문은 건너뛴다.

**Q1. 문서 종류** (2단계)
- 1차: 기록(회의록) · 결정(ADR) · 요구(PRD·FRD) · 설계(TDD)
- "요구"를 골랐으면 2차로 PRD/FRD 중 확인

**Q2. 입력 소스** — 이 대화 / 파일 경로 / URL / 붙여넣기 / 없음(인터뷰로 채움)

**Q3. 언어** — `user.json` 의 `default_language` 를 기본값으로 제시하고 한 줄로 확인만 받는다.

절대 묻지 않는다: 미리보기 여부(항상 함), 게시 여부(미리보기 후에 사람이 정함), 말투(설정에 있음).

## 2. 재료 수집

Q2에서 정한 소스를 실제로 읽는다(파일 Read, URL은 WebFetch, 대화는 이 세션 컨텍스트). 소스가 "없음"이면 템플릿의 각 섹션 `ask` 문구로 하나씩 인터뷰한다.

## 3. 템플릿 로드 및 필수 항목 확인

`templates/<종류>.json` 을 읽는다. `sections[].required: true` 인 항목마다 재료에서 답을 찾는다. 못 찾은 항목만 모아서 한 번에 되묻는다 — 빈칸을 추측으로 채우지 않는다. `unknown`/미확인 항목은 채우지 못했다고 해서 비워두지 말고 "확인 필요"로 명시해 채운다.

## 4. 용어 적용

`bongvis.team.json` 의 `glossary` 를 재료와 대조한다. `avoid` 목록의 표현이 나오면 `term` 으로 바꾸고, 문서 끝에 "용어 교정" 항목으로 무엇을 바꿨는지 남긴다. 용어집에 없는 새 용어가 재료에 3회 이상 나오면 등재를 제안한다(임의로 정하지 않는다).

## 5. 작성

- front matter: 템플릿의 `front_matter` 필드 채움 (id는 사용자에게 체계가 없으면 잠정 번호를 매기고 확정 아님을 표시)
- 본문: 템플릿 `sections` 순서대로, `style` 을 따른다. 대화 말투(`user.json.tone`)는 본문에 절대 반영하지 않는다 — 수치·근거·미확인 항목은 있는 그대로 쓴다.
- 다이어그램: 템플릿 `diagram.when` 조건을 충족할 때만 넣는다. 조건 미충족이면 넣지 않는다. 한 문서에 3개를 넘기지 않는다 — 넘으면 문서를 쪼갤지 사용자에게 확인한다.
- 문서 간 링크: 관련 문서가 있으면 `related`/`supersedes` 를 채운다. 같은 주제의 기존 문서가 이미 있으면 작성 전에 알리고 개정(`/revise`)으로 유도한다.

## 6. 로컬 미리보기

작성한 마크다운을 그대로 보여준다(Stage 1 — Confluence 연동 전이므로 마크다운 자체가 최종 미리보기). 게시 대상이 `bongvis.team.json` 에 없으면(Stage 1 기본) 여기서 로컬 파일로 저장하고 끝낸다.

## 7. 게시 (게시 대상이 설정된 경우만)

사람이 미리보기를 확인한 뒤에만 "게시할까요"를 한 번 묻는다. 게시 전 질문은 이것뿐이다. Confluence 대상이면 storage format(XHTML) 변환 결과를 다시 보여주고, 변환 중 깨지는 요소(표 병합·Mermaid 매크로·이미지)가 있으면 목록으로 먼저 보고한다. 게시 승인 없이 쓰지 않는다.

## 8. 마무리

저장 경로(또는 게시 URL)를 보고하고, `.bongvis/training.json` 에 이 문서 종류의 피드백 대기 상태를 남긴다(`/train` 이 나중에 채움).
